MelonInstaller

MelonInstaller is used to Build, Install, and Update Melon. It has translation support for EN and ES. You can switch language by using the argument: 

MelonInstaller -lang ES

Versions

Every release belongs to a branch and has a four part version number. Each branch counts its own builds, adding one to the last number every build: 

Beta 0.9.0.0  →  Beta 0.9.0.1  →  …  →  Beta 0.9.0.6
                                          ↓ promoted
                                     Stable 0.9.0.1

On GitHub, releases are tagged as the branch, a dash, then the version, and titled with a space:

TagTitle
Beta-0.9.0.0Beta 0.9.0.0
Stable-0.9.0.1Stable 0.9.0.1

Version numbers only order releases within a branch. MelonGUI, MelonCLI, and check-for-updates show the running version.

Branches

Branches aren't hard coded: the installer reads every release tag and offers each branch that has at least one release. Today that's just Beta. Once a Stable release exists it becomes the default for new installs. 

MelonInstaller -branch Beta                     # latest Beta
MelonInstaller -branch Beta -version 0.9.0.3    # a specific Beta
MelonInstaller -version Stable-0.9.0.1          # a full tag picks the branch too

The installed branch and version are kept in melon-release.json in the install folder.

Switching Branches

You can move to another branch at any time. If the target has a lower version number than what's installed, the installer warns you first and asks to continue: 

[!] Switching from Beta 0.9.0.6 to Stable 0.9.0.1 installs an older version number. ...
Continue? (y/N)

When there's no one to ask (the -update flow, or input is redirected), add -force to switch anyway. Server updates never switch branches on their own.

Installing

Run MelonInstaller with no arguments. It asks for a branch and an install path, then installs the latest release on that branch. When it finishes it opens MelonGUI, or MelonCLI in the same terminal if you ran it from one.

ArgumentDoes
-installPath <path>Install here without asking.
-branch <name>Install from this branch.
-version <version or tag>Install this release instead of the latest.
-localPath <zip>Install from a downloaded release zip.
-forceSwitch to a lower version on another branch without asking.
-noLaunchDon't open MelonGUI or MelonCLI afterwards.

Each release has one zip per platform:

AssetContains
Melon-win-x64.zipServer, Controller (MelonGUI), CLI, Installer
Melon-linux-x64.zipServer, CLI, Installer
Melon-osx-arm64.zipServer, CLI, Installer
MelonInstaller-<platform>The installer on its own

Updates

Whenever you ask Melon to update, it checks GitHub for the newest release on its own branch. If that version number is higher, it launches MelonInstaller and closes itself. On Windows the installer stages the new bundle and swaps Server, Controller, CLI, and Installer together, then restarts Melon.

You can call for an update yourself with:

MelonInstaller -update -installPath <installationDir>

Add -restart to start the server again afterwards:

MelonInstaller -update -restart -installPath <installationDir>

Building

MelonInstaller builds a release bundle with -build. Point it at the Code folder: 

MelonInstaller -build -buildPath ./Code -branch Beta -outputPath ./Build
[+] Building Beta 0.9.0.3
[+] Build Package created at ./Build/Melon-Beta-0.9.0.3-win-x64.zip
[+] Publish it as GitHub release tag Beta-0.9.0.3 (Beta 0.9.0.3)

The build count lives in Code/MelonInstaller/BuildVersions.json, so commit it after a build: 

{
  "base": "0.9.0",
  "branches": { "Beta": "0.9.0.3" }
}
ArgumentDoes
-branch <name>The branch to number against. Defaults to Beta.
-baseVersion 0.10.0Start a new line at 0.10.0.0. A four part version is used as is.
-outputPath <dir>Where the zip goes. Defaults to Build.
-versionFile <file>Use another build count file.

Publishing a GitHub release with a Branch-Version tag runs the Release bundles workflow, which stamps the version, builds all three platforms, and attaches the zips and installers.
